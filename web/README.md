# AskGPT notes

Web app for the [KOReader AskGPT plugin](https://github.com/memit0/koreader-ai-plugin). Your highlights, the notes you
wrote on them, and the AI explanations you asked for — all in one place, per
book, synced from your e-reader.

## What it shows

- **Library** — every book you have synced, with counts of highlights, notes and
  explanations.
- **Book** — one page-ordered list. Each entry is the highlighted passage, the
  note you wrote on it, and any explanations recorded against it, including
  follow-up questions.

The device strips its own explanation out of the note before sending, so your
note stays yours and the AI text is not ingested twice.

## Setup

1. Create a Supabase project, then run `supabase/migrations/0001_init.sql`
   against it (SQL editor, or `supabase db push`).
2. Copy `.env.example` to `.env.local` and fill in the three keys from
   **Settings → API**.
3. `npm install && npm run dev`

Deploying to Vercel: set the same variables in the project settings.
`SUPABASE_SERVICE_ROLE_KEY` must **not** be prefixed `NEXT_PUBLIC_` — it bypasses
row level security and is only ever used server-side by the sync endpoint.

## Pairing a reader

Open **/pair**, generate a code, and type it into KOReader under
**Menu → AskGPT → Pair with web app**. Six characters, valid for ten minutes,
usable once. The device gets a long-lived token in exchange; only its hash is
stored here.

If you self-host, point the plugin at your instance by adding
`ASKGPT_SYNC_URL=https://your-instance.example.com` to the plugin's `.env`.

## The device contract

Two endpoints, both taking JSON.

`POST /api/v1/pair` — `{ code, device_uuid, device_name }` → `{ token }`

`POST /api/v1/sync` — `Authorization: Bearer <token>`, and either

```json
{ "books": [...], "items": [...] }
{ "books": [...], "conversations": [...] }
```

Every record carries a client-generated `uuid` that is stable for its lifetime,
and every write matches on `(user_id, uuid)`. That is what makes re-sending a
batch — which happens whenever the reader's wifi drops mid-sync — update in
place rather than duplicate, and it is why the device can retry blindly.

A batch naming a book that was not sent alongside it is rejected with 400 rather
than partially applied, so the device keeps those rows pending and sends them
again with their book.

## Tests

```sh
npm test
```

The fixture in `test/fixtures/payloads.json` is generated by running the **actual
plugin sync code** and capturing what it puts on the wire. Regenerate it from a
checkout of the plugin repo alongside this one:

```sh
cd ../koreader-ai-plugin
lua5.1 test/dump_payload.lua ../koreader-ai-plugin-webapp/test/fixtures/payloads.json
```
 The tests then push those exact payloads
through the real route handler with Supabase faked in memory.

That combination is the point: it fails if either side renames a field, which is
the kind of drift that otherwise stays invisible until a reader in the field
cannot sync. It caught exactly that during development — the device was sending
a local row id where the server needed the book's uuid.
